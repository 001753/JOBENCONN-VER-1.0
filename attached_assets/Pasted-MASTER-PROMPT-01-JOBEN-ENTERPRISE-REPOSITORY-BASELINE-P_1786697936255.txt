============================================================

Karena JOBEN belum dibangun, siapkan foundation yang bersih dan maintainable.

Target foundation:

- deterministic package installation
- deterministic build
- deterministic test execution
- deterministic lint/typecheck jika stack mendukung
- consistent source structure
- environment configuration contract
- safe configuration loading
- centralized error boundary
- structured logging baseline
- health/readiness baseline
- configuration validation
- basic application lifecycle
- architecture documentation

Gunakan stack yang ditentukan PRD.

Jangan mengganti technology stack tanpa alasan yang jelas dan terdokumentasi.

Jika suatu dependency belum diperlukan untuk P0,
JANGAN memasangnya hanya untuk persiapan future feature.

PRINSIP:
MINIMUM DEPENDENCY / MAXIMUM FOUNDATION.

============================================================
4. ARCHITECTURE BASELINE
============================================================

Buat architecture baseline yang mencerminkan PRD.

Pisahkan secara jelas boundary:

PRESENTATION
↓
APPLICATION/API
↓
DOMAIN
↓
PERSISTENCE
↓
INFRASTRUCTURE / PROVIDERS

Jangan mencampurkan business logic ke UI.

Jangan membuat provider-specific logic menjadi domain logic.

Jangan membuat frontend sebagai source of truth.

Tetapkan prinsip:

SERVER = AUTHORITY
DATABASE = DURABLE STATE
PROVIDER = EXTERNAL OBSERVATION SOURCE
UI = PROJECTION OF SERVER STATE

Architecture harus memungkinkan implementasi berikutnya tanpa rewrite besar:

- multi-organization
- tenant isolation
- RBAC
- audit
- provider adapters
- scan orchestration
- evidence
- deterministic evaluation
- remediation
- billing
- AI Gateway

Tetapi fitur-fitur tersebut BELUM BOLEH diimplementasikan pada prompt ini.

bukan dummy success.

============================================================
6. CAPABILITY STATE MODEL
============================================================

Implementasikan atau dokumentasikan capability state model
yang digunakan JOBEN.

Minimum state:

PLANNED
NOT_IMPLEMENTED
EXPERIMENTAL
DEMO
LIVE_VERIFIED

Aturan keras:

Tidak boleh mengklaim capability sebagai LIVE_VERIFIED
hanya karena:

- route tersedia
- UI tersedia
- function exists
- mock berhasil
- fixture berhasil
- seed berhasil
- API mengembalikan 200
- AI menghasilkan jawaban

LIVE_VERIFIED hanya boleh diberikan setelah acceptance gate
yang ditentukan roadmap/PRD benar-benar terpenuhi.

Untuk Master Prompt 01,
foundation capability boleh berstatus:

IMPLEMENTED / VERIFIED

tetapi fitur bisnis tetap:

PLANNED atau NOT_IMPLEMENTED.

============================================================
7. ENVIRONMENT CONTRACT
============================================================

Buat environment contract yang jelas.

Pisahkan:

REQUIRED
OPTIONAL
DEVELOPMENT
TEST
PRODUCTION

Jangan memasukkan secret ke source code.

Jangan membuat:

- hardcoded password
- hardcoded API key
- hardcoded token
- hardcoded database credential
- fake production secret

Jika environment variable belum tersedia,
application harus memberikan error konfigurasi yang jelas,
bukan diam-diam menggunakan secret palsu.

Sediakan .env.example tanpa secret nyata.

Dokumentasikan:

- variable name
- purpose
- required/optional
- expected format
- environment scope

============================================================
8. CONFIGURATION VALIDATION
============================================================

Buat centralized configuration validation.

Application harus gagal secara jelas jika
required configuration production tidak tersedia.

Development/test behavior boleh berbeda,
tetapi perbedaannya harus explicit.

Jangan membuat production fallback ke:

- insecure default
- random undocumented value
- fake credential
- localhost dependency tanpa dokumentasi

Jika SESSION_SECRET / encryption secret / database configuration
diperlukan oleh foundation, perlakukan sebagai secret.

============================================================
9. ERROR HANDLING BASELINE
============================================================

Buat centralized error taxonomy/foundation.

Minimum distinction:

VALIDATION_ERROR
AUTHENTICATION_ERROR
AUTHORIZATION_ERROR
NOT_FOUND
CONFLICT
CONFIGURATION_ERROR
DEPENDENCY_ERROR
INTERNAL_ERROR

Jangan expose:

- stack trace
- secret
- credential
- internal token
- sensitive database information

kepada end user pada production response.

Logging internal boleh memiliki detail teknis yang diperlukan,
tetapi tetap mengikuti redaction policy.

============================================================
10. LOGGING BASELINE
============================================================

Implementasikan structured logging baseline.

Log harus memungkinkan debugging production.

Minimum context jika tersedia:

- timestamp
- severity
- request/correlation id
- route/operation
- environment
- duration
- error code

Jangan log:

- password
- session secret
- API secret
- access token
- refresh token
- raw credentials
- sensitive authorization material

Buat redaction utility bila diperlukan.

============================================================
11. HEALTH / READINESS
============================================================

Sediakan health/readiness foundation.

Bedakan:

LIVENESS
dan
READINESS

Liveness:
application process hidup.

Readiness:
application siap menerima traffic berdasarkan dependency
yang memang diwajibkan oleh environment.

Jangan membuat health endpoint mengatakan "healthy"
jika sebenarnya dependency wajib gagal.

Namun jangan memaksakan dependency future
yang belum menjadi requirement P0.

Dokumentasikan behavior-nya.

============================================================
12. TEST FOUNDATION
============================================================

Siapkan test foundation yang deterministic.

Minimal:

- test command
- build command
- lint/typecheck jika applicable
- basic application startup test
- configuration validation test
- health/readiness test
- error boundary test
- secret redaction test jika utility dibuat

Test tidak boleh bergantung pada:

- real production secrets
- random external API
- uncontrolled external state

Gunakan deterministic test fixtures hanya untuk TEST.

Fixture/seed TIDAK BOLEH dianggap sebagai live capability.

============================================================
13. CI FOUNDATION
============================================================

Siapkan CI foundation yang sesuai stack.

Minimum pipeline:

INSTALL
↓
VALIDATE
↓
TYPECHECK/LINT jika applicable
↓
TEST
↓
BUILD

CI harus fail jika build/test gagal.

Jangan menambahkan pipeline kompleks
yang belum dibutuhkan P0.

Credit-efficient:
gunakan pipeline sederhana dan deterministic.

20. CREDIT EFFICIENCY RULE
============================================================

HEMAT KREDIT ADALAH REQUIREMENT.

Jangan:

- mengulang file inspection yang sudah dilakukan;
- membaca seluruh repository berkali-kali;
- menginstall dependency yang tidak diperlukan;
- membuat file yang tidak diperlukan;
- membuat abstraction berlebihan;
- membuat speculative architecture;
- membangun future module;
- menjalankan test yang sama berulang kali tanpa perubahan.

Gunakan pendekatan:

INSPECT → PLAN → IMPLEMENT → TEST → VERIFY.

Kerjakan dalam batch kecil yang logis.

Jika acceptance criteria sudah terpenuhi,
STOP.

Jangan mencari pekerjaan tambahan.

============================================================
22. DEFINITION OF DONE
============================================================

MASTER PROMPT 01 dianggap DONE hanya jika:

1. repository dapat dipahami;
2. architecture baseline tersedia;
3. application foundation berjalan;
4. configuration tervalidasi;
5. build berhasil;
6. tests berhasil;
7. CI baseline berhasil jika applicable;
8. secret handling aman;
9. logging/error baseline tersedia;
10. capability registry tersedia;
11. P0 readiness document tersedia;
12. tidak ada fake capability;
13. tidak ada future feature yang diklaim live;
14. scope tetap terbatas pada Prompt 01.

============================================================
23. FINAL VERIFICATION
============================================================

Setelah implementation:

1. jalankan build;
2. jalankan test;
3. jalankan lint/typecheck jika applicable;
4. jalankan application;
5. verify health;
6. verify readiness;
7. verify configuration failure behavior;
8. verify secret redaction;
9. inspect git diff;
10. pastikan hanya file yang relevan berubah;
11. pastikan tidak ada accidental future implementation;
12. pastikan documentation sesuai keadaan nyata.

Jika ada failure:
FIX hanya failure yang berada dalam scope Prompt 01.

Jika failure berasal dari dependency/future scope:
DOCUMENT + DEFER.

Jangan memperluas scope.

============================================================
24. FINAL REPORT
============================================================

Pada akhir pekerjaan berikan laporan ringkas:

A. IMPLEMENTED
- daftar konkret pekerjaan yang benar-benar selesai.

B. VERIFIED
- command/test yang berhasil.

C. FILES CHANGED
- daftar file yang berubah dan alasan.

D. CAPABILITIES
- state setiap capability yang relevan.

E. DEFERRED
- pekerjaan yang sengaja tidak dikerjakan
  karena milik Prompt 02+.

F. RISKS
- risiko yang masih terbuka.

G. P0 GATE
- PASS / FAIL
- dengan bukti.

H. NEXT MASTER PROMPT
- jelaskan dependency yang siap diteruskan
  ke Master Prompt 02.
