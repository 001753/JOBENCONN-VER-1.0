Sudah saya identifikasi **roadmap-nya secara mendalam**, bos. Dan setelah melihat roadmap ini, saya akan **mengubah cara kita menyusun 10 master prompt**.

Roadmap ini ternyata jauh lebih matang daripada sekadar daftar fitur. Ia sudah merupakan **engineering execution contract** untuk JOBEN. Sumbernya secara eksplisit menyebut PRD sebagai source of truth, roadmap v3.0, dan repository saat ini belum boleh mengklaim capability `live_verified`. 

## 1. Struktur sebenarnya dari roadmap

Roadmap mempunyai dua lapisan:

### A. Product Phase

```text
P0  Foundation & Readiness
 ↓
P1  AWS Evidence Vertical Slice
 ↓
P1B Provider Kedua + Operational Beta
 ↓
P2  Trust / Auditor / Public Surface
 ↓
P3  Global Expansion
 ↓
P4  ISO 27001
 ↓
P5  GDPR / CCPA
 ↓
P6  AI Questionnaire
 ↓
P7  PCI SAQ Assistant
 ↓
P8  White-label + Auditor Marketplace
 ↓
P9  Hardening + GA
```

Ini bukan urutan kosmetik. P0–P1B adalah **jalur MVP live**, sedangkan P2–P8 adalah ekspansi setelah vertical slice terbukti. P9 adalah GA dan secara eksplisit tidak boleh disamakan dengan MVP beta.

# 2. Yang paling penting: dependency DAG

Ini bagian yang menurut saya harus kita jadikan **tulang punggung semua prompt**.

Roadmap mendefinisikan:

### S0 — Foundation Truth

`M-01 + M-15`

Harus membuktikan:

* multi-organization;
* server-side authorization;
* audit;
* migration;
* secret redaction;
* backup/restore smoke;
* CI;
* hosting verification.

### S1 — Evidence Vertical Slice

`M-02 + M-03 + M-04 + M-05`

Harus membuktikan:

* AWS cross-account verification;
* minimal satu check nyata;
* queue/lock/retry;
* immutable evidence;
* hash re-verification;
* permission denial;
* schema drift.

### S2 — Decision System

`M-06 + M-07`

Harus membuktikan:

* rebuild projection identik;
* freshness/coverage;
* error tidak menjadi pass;
* remediation;
* rescan;
* close/reopen;
* tenant/security regression.

### S3 — Customer Operating Surface

`M-08 + M-09 + M-10`

Harus membuktikan:

* UI/API parity;
* empty/error/degraded state;
* deterministic report;
* signed access;
* dedupe/delivery latency;
* audit.

### S4 — Governance Surface

`M-11 + M-12`

Harus membuktikan:

* human approval;
* official-source provenance;
* scoped/time-bound auditor access;
* stale/demo exclusion;
* publish/revoke.

### S5 — Commercial + Assistant

`M-13 + M-14`

Harus membuktikan:

* webhook inbox/reconciliation;
* entitlement deny;
* citation/refusal golden set;
* cost ceiling;
* provider fallback safety.

### S6 — Operational Readiness

`M-15`

Harus membuktikan:

* incident exercise;
* restore drill;
* queue controls;
* SLO telemetry;
* capability diff;
* on-call/runbooks. 

**Ini sangat penting:** roadmap mengatakan dependency DAG ini **bukan daftar fitur yang boleh dilewati**. Setiap slice harus selesai end-to-end sebelum slice berikutnya dapat `live_verified`.

# 3. Ada perbedaan penting antara "Phase" dan "Master Prompt"

Ini yang saya lihat setelah membaca roadmap.

**Jangan membuat:**

> Prompt 1 = Phase 0
> Prompt 2 = Phase 1
> Prompt 3 = Phase 2
> dst.

Karena Phase terlalu besar.

Sebaliknya:

### 10 Master Prompt = execution packages

Satu master prompt bisa mengerjakan beberapa work package **yang memang berada pada dependency yang sama**, tetapi **tidak boleh melompati gate**.

# 4. Ada prinsip yang sangat saya suka dari roadmap ini

Roadmap **melarang fake progress**.

Secara eksplisit:

> tidak boleh ada `pass`, `met`, `score`, `verified`, `paid`, atau `published` yang berasal dari frontend, seed, fixture, AI, default value, atau optimistic response. 

Dan:

> provider error, permission error, timeout, schema drift, stale, partial, dan missing evidence **tidak boleh menjadi pass**. 

Ini menurut saya justru bisa menjadi **competitive advantage saat judging**.

Karena kita dapat mengatakan:

> **JOBEN tidak mengarang compliance.**

# 5. Roadmap juga sudah mengantisipasi masalah demo

Ada tiga namespace yang wajib diuji:

```text
LIVE CUSTOMER
      +
PROVIDER SANDBOX
      +
ISOLATED DEMO
```

Data demo **tidak boleh digunakan untuk membuktikan capability live**. 

Ini sangat bagus.

Jadi nanti ketika membuat demo hackathon, kita bisa punya:

### Demo mode

untuk juri melihat produk cepat.

Tetapi labelnya harus jelas.

Dan:

### Live verified

harus berasal dari provider/sandbox yang benar-benar dieksekusi.

## Kesimpulan saya

**Roadmap ini sudah sangat bagus. Saya tidak akan menggantinya.**

Yang akan kita lakukan adalah **menerjemahkan roadmap ini menjadi 10 execution master prompts tanpa merusak dependency DAG-nya.**

Dan saya menemukan aturan penting yang akan menjadi **kontrak di setiap prompt**:

> **Tidak ada feature jumping, tidak ada fake/live claim, tidak ada rebuild, tidak ada mock yang menyamar sebagai capability nyata, dan setiap master prompt harus berhenti setelah scope + gate-nya selesai.**

Roadmap juga menetapkan bahwa `CapabilityRecord`, decision/RFC log, provider matrix, data classification, threat model, test evidence, runbook, dan customer limitation harus diperbarui setiap phase. 

**Jadi sekarang saya belum membuat Prompt 01.**
Kita sudah punya blueprint yang cukup presisi. Langkah berikutnya tinggal kita eksekusi **Master Prompt 01**, dan saya akan membuatnya berdasarkan **P0 + WP-01**, bukan membuat project JOBEN dari nol secara membabi buta.
