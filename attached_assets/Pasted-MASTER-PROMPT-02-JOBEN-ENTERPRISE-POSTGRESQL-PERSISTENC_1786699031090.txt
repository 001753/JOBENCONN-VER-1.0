============================================================
15. ORGANIZATION SCOPE
============================================================

Ini adalah requirement CRITICAL.

Setiap customer-owned persistence entity
harus mempunyai organization scope
secara eksplisit atau melalui relationship
yang dapat diverifikasi secara deterministik.

Jangan percaya:

organizationId dari request body
sebagai bukti authorization.

Request context akan divalidasi
pada application/service layer.

Repository layer harus membantu mencegah
accidental unscoped access.

============================================================
16. SCOPED REPOSITORY FOUNDATION
============================================================

Buat repository/data-access abstraction yang
mendukung tenant-scoped query.

Contoh konsep:

OrganizationContext

dan

ScopedRepository<T>

atau pattern equivalent
yang sesuai architecture existing.

Goal:

customer-facing service TIDAK boleh secara normal
melakukan query global terhadap customer data
tanpa explicit system-level authority.

Jangan membuat abstraction terlalu kompleks.

Gunakan typed repository/service boundary
yang sederhana dan dapat dipahami.

ANTI-PATTERN:

db.organization.findMany()

langsung dari route customer.

PREFERRED:

organizationRepository.list(ctx)

dengan organization scope berasal dari
validated actor context.

Actor context akan dikerjakan Prompt 03,
tetapi repository contract harus siap menerimanya.

============================================================
17. SYSTEM VS CUSTOMER ACCESS
============================================================

Bedakan dua kategori:

CUSTOMER-SCOPED ACCESS
dan
SYSTEM-LEVEL ACCESS

Repository contract harus membuat perbedaan ini jelas.

System jobs masa depan boleh membutuhkan
cross-organization operations,
tetapi harus memiliki explicit system context.

Jangan membuat:

organizationId = undefined
berarti "semua organisasi".

Jangan membuat default query:

findMany()

untuk customer path.

Default customer behavior:

DENY / SCOPED.

19. CONCURRENCY / VERSIONING
============================================================

Tambahkan optimistic concurrency/versioning
untuk mutation penting.

Minimal foundation:

version integer atau equivalent.

Tujuan:

mencegah lost update.

Jika mutation dilakukan terhadap row
yang sudah berubah:

RETURN CONFLICT.

Jangan silently overwrite.

Repository/service contract harus mendukung
conditional update.
