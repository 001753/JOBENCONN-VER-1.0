PEKERJAAN, PERSIS URUTAN INI:
1. Siapkan SATU akun AWS disposable/controlled (akun sandbox/test terpisah
   dari akun production apa pun) khusus untuk pembuktian ini.
2. Deploy CloudFormation role read-only (`/public/aws/joben-readonly-role.yaml`
   jika sudah ada di repo; jika belum ada, buat sesuai kontrak §7.4: trust
   policy membatasi JOBEN_AWS_ACCOUNT_ID + External ID unik, dan policy
   custom HANYA berisi action minimum untuk check ini).
3. Hubungkan integration ini ke aplikasi dengan Role ARN + External ID
   (bukan access key). Simpan `Integration.credentialsRef` sebagai reference
   terenkripsi, bukan credential mentah.
4. Jalankan STS AssumeRole SUNGGUHAN dari aplikasi ke akun sandbox tersebut:
   a. Buktikan STS identity verification berhasil dan account ID yang
      didapat cocok dengan account ID yang diharapkan.
   b. Uji account mismatch: coba assume role dengan External ID salah atau
      ke account ID yang tidak sesuai — HARUS ditolak oleh AWS (rekam error
      asli AWS, bukan validasi aplikasi semata).
   c. Buktikan credential STS hasil AssumeRole tidak pernah ditulis ke
      database/log/disk — hanya hidup di memory selama durasi scan (audit
      kode + audit log runtime untuk memastikan tidak bocor).
5. Jalankan `iam:GetAccountSummary` sungguhan pada akun sandbox tersebut
   melalui pipeline evaluator yang sudah ada. Simpan:
   - Observation mentah dari AWS (redacted secukupnya untuk dokumen).
   - Evidence hash (via pipeline TASK-03 — pastikan evidence ini benar-benar
     tersimpan di object storage WORM, bukan lagi di adapter lokal).
   - Freshness timestamp, coverage (resource apa saja yang tercakup), scan
     ID, checkId + checkVersion, evaluator version, dan provenance lengkap
     (endpoint, permission yang dipakai, source revision dokumentasi AWS).
6. Jalankan skenario permission-negative: cabut permission
   `iam:GetAccountSummary` dari role sandbox tersebut (atau attach deny
   policy), jalankan ulang scan, dan BUKTIKAN hasilnya adalah error/
   INSUFFICIENT_EVIDENCE — BUKAN PASS dan BUKAN FAIL dengan asumsi kondisi
   buruk. Ini adalah test paling kritis: jika hasilnya secara diam-diam
   menjadi PASS atau default value, task ini GAGAL dan harus diperbaiki
   sebelum lanjut.
7. Kembalikan permission, jalankan tenant-isolation negative test: coba akses
   evidence/finding integration ini dari tenant/organization lain di
   aplikasi — HARUS ditolak di HTTP boundary dan service boundary (regression
   terhadap hasil TASK-02).
8. Lakukan controlled-account manual comparison: bandingkan hasil evaluator
   otomatis dengan pengecekan manual langsung di AWS Console/CLI untuk akun
   sandbox yang sama pada waktu yang berdekatan — pastikan hasilnya konsisten
   secara logis (root MFA aktif/tidak aktif sesuai kondisi nyata akun).
9. Re-run scan yang sama minimal dua kali tanpa perubahan kondisi akun.
   Buktikan idempotency: hasil evaluation dan projection deterministik/identik
   (bandingkan checkId, checkVersion, hasil pass/fail, dan struktur evidence
   — timestamp boleh berbeda, hasil evaluasi tidak boleh berbeda).
